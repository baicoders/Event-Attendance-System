# Robust student import implementation report

## Architecture and integrity

The [initial audit and plan](../superpowers/plans/2026-10-25-robust-student-import.md)
records the baseline and gaps. The final pipeline is browser worker parse → canonical
CSV plus optional sheet metadata → server parsing and snapshot-prefetched identity/
group resolution → paginated preview → administrator confirmation → signed review
revalidation under the existing PostgreSQL roster lock → bounded writes → atomic
immutable receipt → result/history. No production dataset was used or changed.

New students require first/last name and USN (existing 11-character text rule) or
12-digit LRN. Identifier namespaces and legacy QR IDs resolve together. Split
identities, repeated source identifiers/canonical targets, replacement identifiers
and conflicting existing names block the entire file. Similar names never merge.
Case/Unicode/whitespace-equivalent names are permitted. New internal IDs are
generated by Prisma; bulk returned IDs are mapped by exact code, never result order.
Unique database constraints remain the last line of defense; supported mutations
share the roster lock. Concurrent different commands revalidate after the lock,
so overlapping stale commands cannot both create identities.

Blank optional fields preserve stored middle name, identifiers, school/year values
and academic groups. Unknown groups block; explicit administrator Group creation
remains a separate action. No implicit seeding occurs. The custom membership table,
position, attendance and canonical QR IDs remain untouched. Updates only include
changed students; unchanged timestamps stay stable. Excluded enrollment statuses
block review with source-row diagnostics, rather than being silently reintroduced.

| Field | Create | Existing student / blank cell |
| --- | --- | --- |
| USN/LRN | At least one valid exact code | Add only an absent identifier; replacing one conflicts; blank preserves |
| First/last name | Required | Conflicting names block; equivalent spelling/case may update; blank blocks |
| Middle name | Optional | Fill when absent; conflicting supplied name blocks; blank preserves |
| School/year | Optional, schema validated | Nonblank valid value updates; blank preserves |
| House/section/program/department/strand | Resolve existing matching-category slug | Nonblank replaces that category; blank preserves |
| Custom group/position | Outside academic import | Never modified by academic import |
| Attendance/internal QR ID | Generated canonical ID for new record | Never replaced or detached |
| enrollmentStatus | Optional validation metadata | Recognized excluded status blocks the file; never clears student data |

The default write batch is 250, optionally configured with
STUDENT_IMPORT_BATCH_SIZE=1..1000. Creates use createManyAndReturn, updates and the
existing academic join table use parameterized set operations. All batches and
receipt construction/insertion/runtime validation share one transaction. A failure
after earlier batches rolls back everything. Actual provisional batch progress
never implies commit. Callback/connection loss does not abort database work or
fabricate rollback. Exact actor/UUID receipt replay performs no roster reads/writes,
including old v1/v2 commands under tighter current parsing policy.

## Components

- import/classify, csv and contract: strict identity/name/status rules, bounded
  parsing, exact source rows, review schema and optional sheet metadata.
- import/writeBatches and server: bounded set writes, existing locks/revalidation,
  preserved identities/relationships, authenticated historic replay before new caps.
- import/xlsx, parseSource, readSource and source.worker: bounded XLSX conversion
  and off-main-thread file parsing/hash. XLSX remains a bounded whole-document
  parser; the browser transport is canonical CSV, independently validated server-side.
- commit route and progressContract: compatible JSON or bounded NDJSON, actual
  progress, validated stream termination, honest unknown outcomes.
- StudentImporter, ImportSourceStep, ImportReviewStep, ImportResult: instructions,
  paginated exception review, complete summary, formula-safe issue download,
  provisional progress and metadata-only refresh recovery.
- benchmark and test fixtures: synthetic disposable PostgreSQL, HTTP and browser
  loads, fault/rollback/concurrency/replay and relationship-preservation evidence.

## Measured performance

Development host: Linux, Node 22.19.0, Intel i5-8350U, local PostgreSQL 17.11 over
TCP port 5433. Other build/test processes competed for resources. Results describe
this environment; production sizing/network latency requires deployment QA.

| Rows | Mixed service commit | Commit queries | HTTP all-new preview / commit |
| ---: | ---: | ---: | ---: |
| 1,000 | 1.92 s | 29 | 254 ms / 1.91 s |
| 3,000 | 3.78 s | 63 | 351 ms / 5.33 s |
| 5,000 | 8.85 s | 101 | 520 ms / 14.84 s |
| 10,000 | 11.38 s | 188 | 4,127 ms / 25.67 s |

Mixed service datasets contain 50% new, 25% updates and 25% unchanged, with USN-only,
LRN-only and dual identifiers. One importer connection was observed at every size,
with a pool cap of two and a separate one-connection observer. At 10k the sampled
RSS and process-lifetime high water were approximately 650 MiB, including fixture
datasets and retained previous-size heaps. RSS snapshots are not a hard production
ceiling. Byte/row/cell/ZIP/coordinate/element bounds limit input expansion; no
unbounded write concurrency or per-row write queries remain. The 100-student
regression reproduced 414 queries before batching and enforces at most 50 afterward.

The [raw scale evidence](student-import-scale.md) records parsing+hash, isolated
state/classification, SQL time, query counts, batch intervals, RSS observations and
connection utilization. Separate phase passes are not additive service timings.
The HTTP run records transaction observations of 1.90/5.29/14.61/25.33 seconds;
receipt response bytes are 348392/1048392/1748392/3498397 respectively. The 10k
receipt occupies 314894 compressed JSONB bytes (3827806 uncompressed JSONB text).
HTTP RSS increases of roughly 34/43/66/100 MiB are snapshots, not peak bounds.

Concurrent attendance scans at 3k/5k/10k encountered the existing confirmed-rollback
503 response and made no record changes. Explicit post-import retries succeeded.
No queue is justified by these request durations, but imports must run outside
active scanning and deployment request/proxy allowances must be checked.

## Verification and independent review

All database load/failure tests provision unique disposable test_* databases from
TEST_DATABASE_URL, apply real migrations and delete only their own fixtures.
No raw enrollment files are committed or used in synthetic stress tests.

Validated scenarios include 100 new grouped records, 1k/3k/5k/10k HTTP creates,
1k/3k/5k/10k mixed imports, identical reupload/no-op timestamps, duplicate USN/LRN,
split identity, missing identifiers, conflicting names, known/unknown groups,
excluded/missing statuses, malformed files, blank preservation, custom positions,
attendance and QR stability, overlapping commands, lost response, actor revocation,
stale preview, third-batch failure and receipt failure rollback. Browser coverage
includes keyboard file selection, 375px layouts, 5k parsing/pagination/search and
actual confirmation/progress/receipt plus database verification of all 5,000 rows,
downloaded issue CSV, actual XLSX upload with sheet/row/leading-zero identity,
refresh metadata-only recovery, Check result, exact frozen retry, and source/account
race protection. Final gate outputs are recorded in the plan evidence ledger.

The interruption gate SIGKILLs the real Next process after two tentative batches
while the third is held at an independently observed PostgreSQL lock. It verifies
zero persisted students/receipt, restarts the server, checks the absent receipt,
then executes and replays the same frozen command exactly once (501 students).

Independent reviews examined the combined implementation and found two concrete
issues, both addressed with regression tests: new parser limits preventing historic
receipt replay, and encoded XLSX coordinates bypassing pre-allocation bounds.
Additional ZIP-directory consistency and workbook sparse-index protections defend
the same parser allocation boundary.

Repository lint has five errors in unchanged baseline files: StepIndicator.tsx,
getDynamicFilters.ts, and DataTableStates.tsx; nine warnings also remain. These files
match the base commit. Changed import files pass focused ESLint. The broad Node
invocation initially passed 279 tests but misconfigured three test files: React
render tests need normal conditions, and eventReport needs dotenv preloaded.
Rerunning those files correctly passes all 13 tests. These runner configuration
failures are not hidden as product regressions.

The corrected broad server-compatible invocation subsequently passed **290 tests**;
the two separately run React render files passed **11 tests**. Source-diagnostic
download additions were also verified with their complete six-test report suite.

## Deployment and limitations

No new schema migration, worker service, queue, Redis, or mandatory environment
variable is introduced. Install the locked ExcelJS/fflate dependencies and deploy
the coordinated UI/API build. Optional STUDENT_IMPORT_BATCH_SIZE defaults to 250.
The existing student identifier/receipt/custom-group migrations must already be
deployed. Backup tests need PostgreSQL clients at least as new as the server;
the development host's default version 14 was unsuitable for PostgreSQL 17, so
the restore gate used the existing PostgreSQL 17 image as client tooling.

New files are capped at 10k students/10 MiB; XLSX expanded content is capped at
32 MiB total, 16 MiB per entry, 128 entries and bounded XML/worksheet dimensions.
Only one populated sheet, canonical headers and plain-text identifiers are accepted.
Merged/multiline/formula/date/link/error identifier cells require source correction.
No arbitrary enrollment column mapping, number-to-identifier repair, fuzzy merge,
partial-valid-row import, destructive clearing, or in-flight cancellation is added.

Refresh can recover only the command reference; retry after refresh requires a fresh
review if no receipt is found, after resolving any still-running command. The UI
explicitly states that a missing receipt is inconclusive. Proxy buffering can delay
progress without changing atomicity. Receipt times are server observations before
COMMIT acknowledgment, so displayed duration is approximate.

## Manual nonproduction QA

1. Point TEST_DATABASE_URL at a dedicated PostgreSQL maintenance database, never
   production. Install matching client tools; build the application.
2. Run pnpm test:student-import, pnpm benchmark:import-scale and the documented
   HTTP/browser fixture with --large --browser. These provision their own databases.
3. For interactive QA use a separate disposable application database, apply all
   migrations, create an ADMIN and deliberately seed canonical groups. Generate
   synthetic USN/LRN/name rows; never copy institutional personal information.
4. Upload 5k canonical CSV, verify counts/page size, then confirm. Observe tentative
   batch counts followed by a receipt; query exact student/identifier/group counts.
5. Reupload unchanged CSV; verify no writes/timestamp changes. Import a subset with
   blank house/section/program/department and confirm preservation of those values,
   custom memberships/positions, attendance and QR codes.
6. Add duplicates, split identifiers, conflicting names, unknown groups and the four
   excluded statuses. Verify zero writes, explicit blockers and formula-safe issue
   report rows/actions. Correct/remove rows and perform a fresh review.
7. Upload text-identifier XLSX with a blank row and verify sheet/physical-row labels;
   reject numeric/scientific/formula identifiers and malformed/oversized archives.
8. Change a matched student/group after preview; confirmation must reject stale
   review without writes. Simulate response loss after a committed request; Check
   result and exact retry must return the same receipt without repeated writes.
9. Refresh after an unknown outcome; verify reference-only recovery and disabled
   retry. Check result, verify current roster/history, and resolve any in-flight
   command before beginning a new review. Do not infer rollback from missing receipt.
10. Repeat at 10k while observing memory, connections and actual deployment timeout/
    proxy behavior. Schedule outside scanning. Validate backups and restore into
    another isolated database before institutional rollout. Leave PR unmerged.
